Week 2：サードパーティ API 用の MCP サーバーを構築する

課題概要

サードパーティ API をコーディングエージェントから利用できるようにする MCP サーバーを構築してください。API を扱う部分自体は簡単です。評価対象となるのは エージェントにとっての使いやすさ（agent ergonomics）、つまりモデルが適切なツールを選び、正しく呼び出し、失敗した場合に復旧できるかどうかです。さらに、ラップする価値のある API の多くは固定キーでは認証できないため、実際に動作する OAuth フローも必要です。

学習目標

  • スキーマと説明文しか見られないエージェントを利用者として想定し、ツールのインターフェースを 設計 する。
  • 長時間稼働するサーバー内で、OAuth トークンの取得、キャッシュ、更新を 実装 する。
  • 自分の設計上の選択によって、エージェントの実際の動作がどう変わるかを 観察 する。

教材

  • FastMCP：今回の構築に使用するもの。
  • MCP 仕様：ツールアノテーション、トランスポート、エラーのセマンティクス。
  • MCP サーバーのリファレンス実装：自分で書き始める前に、この中から1つ読んでください。

Part I：サーバーの構築（25点）

OAuth 2.0 を使用する API を1つ選んでください。GitHub、Google（Gmail／Calendar／Drive）、Notion、Linear、Slack、Spotify、Strava は、いずれも条件を満たします。自分が実際に使っているものを選んでください。そのほうが、ツールが何をすべきかを適切に判断できます。

要件：

  • 少なくとも3つのツールを用意し、それらが 連携（compose） できること。つまり、あるツールの出力を別のツールの入力として使える必要があります（例：search_x が返す ID を get_x(id) が受け取る）。
  • 実際の状態を変更する 書き込みツールを少なくとも1つ用意すること。
  • コードは week2/ 内に置き、stdio 経由で動作し、ドキュメントに記載した1つのコマンドで起動できること。

Part II：エージェントにとっての使いやすさ（30点）

ここがこの課題の本質です。以下の項目はすべて、エージェントにはスキーマと docstring しか見えず、それ以外は何も見えないという事実を踏まえたものです。

  • 制約は説明文ではなくスキーマに記述する。 sort: str にして docstring に説明文を加えるより、sort: Literal["stars", "forks"] のほうが優れています。スキーマと docstring が食い違うと、エージェントには理由を説明できないバリデーションエラーが発生します。
  • 出力の形を整える。 API の生の JSON をそのまま渡してはいけません。エージェントに必要なフィールドを選んでください。生のペイロードはトークンを大量に消費し、あなたのインターフェース仕様を他者の API に密結合させます。
  • エラーはトレースバックではなくデータとして扱う。 構造化され、対処に役立つ情報を返してください。また、エージェントが「再試行しない」（不正な ID）場合と「再試行する」（レート制限、一時的なネットワーク障害）場合を区別できるだけの詳細を含めてください。トレースバックはエージェントのターンを終了させますが、{"error": "rate limited, retry after 42s"} なら終了させません。
  • docstring がインターフェース仕様である。 ツール同士を連携できるよう、ID の取得元（例：「list_templates が返す数値 ID」）を明記してください。複数のツールにまたがるワークフローのガイダンスには FastMCP(instructions=...) を使用してください。
  • 書き込みツールには安全装置が必要である。 ツールアノテーション（読み取りツールには readOnlyHint）を使用し、取り消せない操作を行うツールには dry_run パラメーターを設けるか、プレビューと実行を分ける（preview-then-commit）方式を採用してください。

Part III：OAuth（25点）

貼り付けた Bearer トークンではなく、実際の OAuth フローを実装してください。

  • 認可コードをトークンと交換する一連の処理を完全に実装し、トークンを キャッシュ し、有効期限切れ時にはユーザー操作なしで 自動更新 すること。
  • 必要最小限のスコープ。 読み取りしか行わない場合は読み取り専用の権限を要求し、writeup で各スコープが必要な理由を説明してください。
  • リポジトリにシークレットを含めない。 最初のコミットから環境変数を使用して読み込むようにしてください。.mcp.json.example はコミットし、実際に使用する設定ファイルは .gitignore に追加してください。
  • セッションの途中でトークンが無効になった場合に対応する。 長時間稼働するサーバーは、ツール呼び出しの最中にブラウザーを開こうとしてはいけません。代わりに、ユーザーが対処できるエラーを返してください。

Part IV：統合と実演（20点）

  • Claude Code または Cursor にサーバーを登録し、その設定（.mcp.json.example）をコミットする。
  • エージェントが少なくとも2つのツールを連携させて実際のプロンプトに回答する、エンドツーエンドの実行記録を1つ示す。プロンプト、呼び出されたツールと各引数、結果を含めてください。
  • 失敗例を1つ示し、設計したエラー処理によってそれがどう扱われたかを示す。必要なら、不正な ID や失効済みトークンを使って意図的に失敗させてください。
  • Python 関数を直接呼び出すだけでなく、MCP プロトコル経由でサーバーの機能を実際に呼び出すテストを少なくとも1つ用意する。

提出物

week2/ 内に、サーバーコード、.mcp.json.example、テスト、記入済みの writeup.md を配置してください。

評価基準（合計100点）

パート 配点 満点を得るための条件
I. サーバー 25 連携可能なツールが3つ以上あり、そのうち1つが書き込みツールで、ドキュメントに記載されたコマンドで起動できる
II. エージェントにとっての使いやすさ 30 スキーマレベルの制約、整形された出力、構造化されたエラー、ツール連携を説明する docstring、書き込みツールの安全装置
III. OAuth 25 キャッシュと更新を伴う認可コード交換が動作する、必要最小限のスコープとその根拠が示されている、シークレットがコミットされていない、セッション途中のトークン失効を適切に処理できる
IV. 統合 20 コミット済みの設定、実際の連携実行記録、失敗経路の実演、プロトコルレベルのテスト1件

シークレットをコミットした場合、および docstring とスキーマが矛盾するツールがある場合は減点します。
